# ruoyi-agent · 调度智能体内核

对应《智能体调度方案 v0.2》第 3.1 节「调度指令理解」的可运行实现。
一句话进去，编排器判断意图、选工具、过三道闸、把结果拼成一张带证据的卡片。

```
说（打字/语音） → 懂（意图） → 选（工具） → 做并验（MILP + 校验） → 回卡（带 tool_call_id）
```

---

## 一、借了哪些开源架构

不是「用了某个框架」，是「抄了三种已经被验证过的结构」。每一行都能在代码里找到对应。

| 来源 | 借鉴的东西 | 落在哪 |
| --- | --- | --- |
| **LangGraph** | 显式状态机 + 检查点 + 人工中断点 | `AgentOrchestrator.handle()`：`PARSE → GUARD → (CONFIRM) → EXECUTE → COMPOSE → DONE`，拦截后是 `CLARIFY / NEED_CONFIRM / REJECTED`，不是抛异常 |
| **OpenAI Agents SDK** | 工具白名单 + guardrails（输入输出护栏） | `Action` 枚举（固定动作，模型不能自由发挥）、`AgentTool.requiresConfirm()`、三道闸 |
| **Pydantic AI** | 结构化输出优先、解析失败即降级 | `LlmIntentParser`：只认固定 JSON，字段不在白名单就丢；解析失败返回 null → `CompositeIntentParser` 落到规则 |
| **Letta（MemGPT）** | 分层记忆 | 本模块只留了位置（`AgentContext`），记忆在 W6 接 |
| **openEMS / PLC4X**（工业侧） | 设备—通道—点位抽象、统一协议 API | 二期设备层参考，不在本模块 |

**刻意没借的**：AutoGen 的多智能体群聊（单脑多工具更可控）、Dify/Flowise 的可视化编排（不好审计）、
LangChain4j / Spring AI 的整套运行时（这里只需要「发一段话、收一段 JSON」，三十行就够）。

## 二、一次请求发生了什么

```text
POST /agent/chat  {"text":"重跑明天北区A的计划","sessionId":"ui-1"}
  │
  ├─ 闸一 输入长度 ≤ 200 字
  ├─ 解析  LlmIntentParser（无 Key 自动跳过） → RuleIntentParser
  │        得到 Intent{SOLVE_PLAN, dcCode=DC-A, date=2026-11-12, conf=0.92}
  ├─ 闸二 置信度 ≥ 0.5，否则只反问
  ├─ 闸三 写动作 → 返回 NEED_CONFIRM + confirmToken（10 分钟有效）
  └─ 确认后 → SolvePlanTool → DispatchPlanService.generate() → 回卡 + 引用 plan.solve #1005
```

### 三道闸在哪

| 闸 | 位置 | 拦住什么 |
| --- | --- | --- |
| 权限 | 接口层（`/agent/chat` 走 JWT；`/agent/demo/**` 仅演示开关下存在） | 越权调用 |
| 幂等 / 确认 | `AgentOrchestrator` 的 pending 表 + 令牌 | 一句话说两遍就写两份计划 |
| 校验 | 工具内部（求解前查 96 点完整性，求解后落库走原有事务） | 拿半截数据去解 |

## 二点五、多轮上下文

`ConversationStore` 保存每个会话的**上一轮意图**和最近 6 句原话，30 分钟过期。
不存工具返回的原始数据——那些用 runId 回查，避免上下文被大对象撑爆。

实测（同一个 sessionId 连续四句）：

```text
> 北区A现在什么状态          → DC-A 的负荷、电价、装机
> 那南区呢                   → DC-B（动作沿用，站点替换）
> 重跑明天的计划             → DC-B / 2026-11-12，弹确认卡
> （确认）                   → 生成 DPDCB20261111205940001
```

三句话分别验证了三件事：动作继承、站点覆盖、站点继承。

### 为什么站名不让模型猜
第一版把 `dcCode` 交给模型输出，结果「那南区呢」被解析成了 **DC-C**——模型不知道
北/南/东/西与 DC-A..D 的对照，它在猜。

修法不是把提示词写得更长，而是承认这类**确定性实体不该交给模型**：

- 原文里出现「北区 / 南区 / 东区 / 西区 / DC-x」→ 由 `SlotNormalizer` 直接从原文覆盖；
- 「今天 / 明天 / 昨天 / 11月5日」→ 同样由代码解析；
- 模型只负责判断**意图**（是查询还是重跑），不负责识别**事实**。

覆盖时如果模型给的值和原文不一致，回复里会带一行假设：「站点按原文识别为 DC-B（模型给的是 DC-C）」。
不悄悄改，也不让错的继续往下走。

## 二点六、“你是谁”不该甩功能清单

第一版遇到「你是谁」时被判成 HELP，回一份工具列表——用户第一反应就是“这不智能”。

现在拆成两条路：

- **HELP**（“你能做什么”）→ 仍然给能力清单，这时候用户确实想看清单；
- **SMALLTALK**（“你是谁”“介绍一下你自己”）→ 交给模型用自己的话答，两句，不列点。

模型不在时回落一句固定答复，闲聊不能成为链路的故障点。
回复里带 `tokens`，界面显示成 `229 TOK`，这也是“确实调了模型”的凭据。

实测：

```text
> 你是谁
我是这个微网调度系统里的调度智能体，负责把你的话转成调度动作，比如查状态、查计划、重跑或撤销。
意图理解由大模型做，调度计算走本地 MILP 求解器，数字都来自系统查询，我不会编。
[llm · 2433ms · 229 tok]
```

## 三、工具清单

| id | 作用 | 副作用 | 需确认 |
| --- | --- | --- | --- |
| `state.snapshot` | 最近一个采样点的负荷、光伏、电价、装机 | 只读 | 否 |
| `plan.list` | 最近 N 份计划 | 只读 | 否 |
| `plan.detail` | 某份计划的 96 点汇总（SOC 区间、充放、购电） | 只读 | 否 |
| `report.summary` | 某天的成本 / 基线 / 节约 / 碳排 / 消纳 | 只读 | 否 |
| `plan.solve` | 重跑计划并落库 | 写库 | **是** |
| `plan.undo` | 撤销本会话 5 分钟内刚生成的计划 | 写库 | 否（本身就是回退） |
| `strategy.update` | 改储能 SOC 目标 | 写库 | **是** |
| `strategy.list` | 当前启用哪条策略、还有哪些可选 | 只读 | 否 |
| `strategy.select` | 切换启用的调度策略（单选） | 写库 | **是** |

每个工具返回的 `facts` 是**已经格式化好的、带单位的一句话**，回复正文只能由 facts 拼装——
模型不参与数字生成，这就是方案里「不产数字」的落地方式。

### 正文由谁来写

`facts` 只是素材，读起来像清单。正文有两个写法，编排器每次自己选：

| 写法 | 什么时候 | 由谁负责 |
| --- | --- | --- |
| 模板 | 列表类（`plan.list`）、写动作、模型不可用、撰写超时、数字越界 | `AgentOrchestrator` 直接把 headline + facts 拼起来 |
| 模型改写 | 单点结论：`state.snapshot` / `plan.detail` / `report.summary` | `LlmReplyComposer`，只改写、不新增 |

改写之后有一道 **`FactGuard`**：正文里出现的每一个数字，都必须在工具事实或用户原话里找得到
（`7,841` 与 `7841` 视为同一个数）。对不上说明模型在编——常见的是把 873 写成 870、
把 3992 写成 4000——整段弃用，退回模板，并在日志里记下越界的那个数。

界面上的 `解析 LLM · 撰写 LLM` 就是这两步各自的来源；正文下面的「原始数据」是可展开的事实清单，
方便核对模型有没有把话说歪。

### 策略怎么改变求解结果

切换策略不是换个名字，是换一组目标权重。目标函数仍然只有一条
（购电 + 碳排 + 燃气 + 需量 + 储能损耗，见 `DispatchOptimizer`），变的是各项的分量：

| 策略类型 | 侧重 | 权重 | 效果（同一站同一天实测） |
| --- | --- | --- | --- |
| `COMPREHENSIVE` | 成本优先 | 全部按原价加权 | 成本最低 7,595 元，省 14.7% |
| `LOAD` | 削峰优先 | 需量电费 ×3 | 峰值 522 kW（−23%），成本 +574 元 |
| `MICROGRID` | 少买电 | 网购电每度 +0.15 元、光伏自用 +0.30 元、碳排 ×2 | 购电 7,054 kWh（−32%），碳排 −6%，成本 +530 元 |

三个策略是**互斥单选**：`strategy.select` 把目标置为启用、其余停用。求解只认启用中的第一条，
所以不会出现两套权重同时生效。已经算好的计划不会因为切换而改变，要看到差别必须重算。

计划的 `remark` 里带一条**策略签名**（编号 + 类型 + SOC + 消纳率 + 阈值），10 分钟幂等判重时一并比对：
只换了策略或改了参数，就不算「刚算过」，会真的重解，而不是把旧计划端回来。

### 幂等与撤销（W2）

- **幂等**：同一站、同一天、10 分钟内已经解过，`plan.solve` 直接返回旧计划，不再插一份。
  判重在工具里查数据库，不靠内存状态，重启也不失效。
- **撤销**：只认本会话刚建的那一份，5 分钟窗口。撤销会连 `dispatch_plan_item` 一起删，
  删完把会话里的指针清掉，再撤一次会明确告诉你「没有可撤销的计划」。

## 四、怎么开

### 1. 启动

```bash
mvn -DskipTests package -pl ruoyi-admin -am
java --enable-native-access=ALL-UNNAMED -jar ruoyi-admin/target/ruoyi-admin.jar
```

### 2. 接大模型（可选）

不配 Key 也能跑，走规则解析；配上就换成大模型解析，失败自动回落。

```bash
export DEEPSEEK_API_KEY=sk-xxxx
```

本机图省事可以直接写在 `ruoyi-admin/src/main/resources/application-local.yml`（**该文件已在 `.gitignore` 里**，不会进仓库）：

```yaml
agent:
  llm:
    api-key: sk-xxxx
```

打包成产品前，把这两行删掉，改回环境变量注入——`application.yml` 里 `${DEEPSEEK_API_KEY:}` 已经留好了位置。

或改 `application.yml`：

```yaml
agent:
  llm:
    enabled: true
    api-key: ${DEEPSEEK_API_KEY:}
    model: deepseek-chat
```

### 3. 免登录演示（仅本机）

```bash
java -jar ruoyi-admin/target/ruoyi-admin.jar --agent.demo.open=true
curl -X POST http://127.0.0.1:8080/agent/demo/chat \
     -H "Content-Type: application/json" \
     -d '{"text":"北区A现在什么状态","sessionId":"demo"}'
```

生产不打开这个开关，`AgentDemoController` 根本不会注册，接口 404。

### 4. 界面

登录后左侧菜单出现「调度助手」（路由 `/agent/index`），整页是瑞士国际主义版式：
暖白纸底 + 克莱因蓝、等宽小标签、发丝线、大字号轻字重、直角无阴影。

- 左栏对话，右栏三块：SESSION（会话 / 模式 / 工具数 / 消息数）、COMMANDS（可点的例子）、TOOLS（工具清单）
- 每条回复的标签行显示 `LLM · 736MS · 373 TOK · RUN1005`——**TOK 是模型返回的真实 token 用量**，可以直接证明走了大模型
- 写动作渲染成一张确认单（黑底标题 + 参数列表 + 两个按钮），不是气泡
- 语音走浏览器 Web Speech API，不支持的浏览器会提示改用文字

页面挂在 `constantRoutes` 上，不依赖数据库菜单，装好就能进。
若要按权限控制，再往 `sys_menu` 插一行、把路由改成动态加载即可。

## 五、演示脚本（照着念）

| # | 你说 | 期望看到 |
| --- | --- | --- |
| 1 | 北区A现在什么状态 | 标题里就带日期；给最新一点 + 全天负荷峰值、光伏最大出力与发电量、电价区间 |
| 1b | 北区今天什么状态 | 同上，但只查今天；库里没有今天就直接说「没有 X 的数据，遥测只覆盖 A ~ B」 |
| 2 | 那南区呢 | 换成 DC-B，动作沿用上一轮（这一句证明上下文真的生效） |
| 2b | 那昨天的呢 | 站点不变、日期换昨天；只有条件、没有动作词也能接上 |
| 3 | 重跑明天的北区A计划 | 弹确认卡：站点 DC-A、日期明天；**此时什么都没写库** |
| 3b | （明天没有遥测时确认） | 「2026-11-13 只有 0 个采样点，凑不齐 96 点没法求解」——不会偷偷拿最近一天顶替 |
| 4 | （点「确认执行」） | 「计划已生成」，末尾提示 5 分钟内可撤销 |
| 5 | 再问一次「重跑明天的北区A计划」并确认 | 「计划已存在，直接复用」——10 分钟内不会插第二份 |
| 6 | 撤销 | 「计划已撤销」，连 96 条明细一起删 |
| 7 | 再说一次「撤销」 | 「这个会话里还没有可撤销的计划」——不会误删别的 |
| 8 | 昨天省了多少钱 | 成本 / 基线 / 降幅 / 碳排 / 消纳，末尾带「来源 report.summary #1002」 |
| 9 | 把储能余量改到 20% | 弹确认卡（参数回显 20%）；确认后回「65% → 20%，下次求解生效」 |
| 10 | 改回 65% | 把策略恢复原值，回执里写明「20% → 65%」 |
| 11 | 现在用的是哪条策略 | 当前启用的策略 + 权重说明 + 其余可选策略与参数 |
| 12 | 换成削峰那条策略 | 确认卡「待确认：切换调度策略」；确认后回「成本优化 → 负载均衡」并说明生效时机 |
| 13 | 重跑今天北区的计划 | 用新策略重解，**不会复用**切换前的计划；回执带「策略：负载均衡（STR002）· 削峰优先」 |

第 3 步是关键：**没点确认之前，数据库不会多任何一行**。
第 5 步是第二个关键点：**重复说同一句话，不会产生第二份计划**。
第 2 步是第三个关键点：**上下文不是靠把整段对话塞给模型，而是存上一轮的结构化意图**。

## 六、已知边界

- **语音**：一期在浏览器侧（Web Speech），Chrome/Edge 可用；Firefox 与内网受限环境会降级到文字。服务端只留了配置位。
- **大模型**：不配 Key 时自动落到规则模式；配了之后 `/agent/health` 显示 `parser=llm`。
- **记忆**：只做了「工作记忆」（上一轮意图 + 最近 6 句）。情景记忆、站点画像、偏好这三类在 W6。
- **checkpoint**：pending 表与上下文都在内存里，重启即失效；落库到 `agent_run` 是 W2 的活。
- **工具层与业务耦合**：`com.ruoyi.agent.dispatch` 依赖 `ruoyi-system`，物理拆分（core 零依赖）放在 W7–W8。
- **Key 的存放**：只走环境变量 `DEEPSEEK_API_KEY`，仓库里永远是空串。不要把 Key 写进 yml 或提交记录。
- **改参数的范围**：`strategy.update` 目前只开放储能 SOC 目标一项；消纳率下限、转移阈值没开，避免一次改动影响面过大。
- **日期**：读类工具（状态 / 计划列表 / 计划明细）都按槽位里的日期查，没给日期才回落到「库里最近一天」；
  查不到就明说覆盖区间和下一步，**不拿别的日期顶替**。写类工具同理——指定的那天凑不齐 96 点就拒绝求解。
- **模型写正文的代价**：多一次调用，单次回答约从 0.4 s 涨到 1.2~1.6 s。数字守门员只能管住数字，
  措辞里的过度结论（“运行平稳”）靠提示词约束，属于尽力而为。
- **数据新鲜度**：演示库只会在表为空时自动生成历史。系统时钟往前走之后，`POST /dashboard/bootstrap`
  （首页「一键生成演示数据」）会把每个站点缺的日期补到今天，不覆盖已有采样点。

## 七、测试

```bash
mvn -o test -pl ruoyi-agent -am -Dtest=RuleIntentParserTest,AgentOrchestratorTest \
  -Dsurefire.failIfNoSpecifiedTests=false
```

19 个用例：13 个解析用例覆盖示例话术（相对日期、站名、计划编号、数量、解释、帮助、听不懂），
6 个编排用例覆盖确认令牌、幂等、取消，以及「只改了日期或站点的追问要沿用上一轮动作、并把日期传进工具」。
