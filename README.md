# 数据中心电力调度系统 · 调度智能体模块

把一句话变成可执行、可审计的调度动作：**意图解析 → 工具调用 → 确认与幂等 → 数字溯源 → 带证据的回复**。

本仓库是「面向数据中心的电力调度系统」（校级大学生创新创业训练项目，2025.10–2026.10）中，调度智能体模块与调度优化内核的公开片段。完整系统依赖内部工程，未在本仓库提供。

---

## 背景

数据中心的用电负荷有相当一部分是「可延迟的」：批处理、模型训练、日志归档这类任务，只要在时限内完成，就可以挪到电价低谷时段执行。这部分柔性资源如果被写进调度模型，就能在业务总量不变的前提下降低电费、削峰、减少碳排。

本模块解决的是最后一公里的问题：调度员不该为了改一个参数去翻五个页面。他可以像跟同事说话一样说「把储能余量改到 20%」，系统把他这句话变成一次可审计的写操作。

## 一句话进来，发生了什么

```text
POST /agent/chat  {"text":"重跑明天北区A的计划","sessionId":"ui-1"}
  │
  ├─ 闸一  输入长度 ≤ 200 字
  ├─ 解析  LLM 优先（DeepSeek）→ 失败/无 Key 回落规则解析
  │        Intent{SOLVE_PLAN, dcCode=DC-A, date=2026-11-12, conf=0.92}
  ├─ 闸二  置信度 ≥ 0.5，否则只反问
  ├─ 闸三  写动作 → 返回 NEED_CONFIRM + confirmToken（10 分钟有效）
  └─ 确认后 → SolvePlanTool → DispatchPlanService.generate() → 回卡 + 引用 plan.solve #1005
```

编排状态机：`PARSE → GUARD → (CONFIRM) → EXECUTE → COMPOSE → DONE`。拦截后落到 `CLARIFY / NEED_CONFIRM / REJECTED`，不抛异常。

## 五个设计取舍

这五条是模块里真正需要判断的地方，也是我在面试里被问最多的部分。

**1. 确定性实体不交给模型。**
第一版把站点编码交给模型输出。用户说「那南区呢」，模型解析成了 DC-C——它不知道「南北」和 DC-A..D 的映射，它在猜。修法不是把提示词写得更长，而是承认这类实体不该交给模型：原文出现「北区/南区/DC-x」、日期出现「今天/明天/11月5日」，一律由代码从原文覆盖；模型只判断意图（查询还是重跑）。覆盖时如果与模型给的值不一致，回复里带一行说明，不悄悄改。

**2. 模型只负责措辞，不负责数字。**
正文交给模型改写更好读，但模型会把 873 写成 870、把 3992 写成 4000。所以加了一道 `FactGuard`：正文里每个数字必须能在工具返回的事实或用户原话里找到（`7,841` 与 `7841` 视为同一个数），有一个对不上就整段弃用、退回模板，并在日志里记下越界的那个数。

**3. 写操作先出确认卡，且必须幂等。**
「重跑计划」是写库操作。没点确认之前，数据库不会多任何一行；同一句话连说两遍，10 分钟内直接复用旧计划，不会插第二份。判重键是「站点 + 日期 + 策略签名 + 参数」，签名变了就真的重解。

**4. 三道闸分三层，各拦一类错误。**
权限在接口层（JWT）；确认与幂等在编排器（pending 表 + 令牌）；数据完整性在工具内部（求解前查 96 点是否齐备，缺一天就明说「凑不齐 96 点」，绝不拿别的日期顶替）。

**5. 读与写的回复走不同路径。**
列表类、写动作、模型不可用时用模板拼装；状态、复盘、计划明细这类「一个问题一个结论」的交给模型改写。改写多一次调用，单次响应从约 0.4 s 涨到 1.2–1.6 s，这是准确性换来的代价。

## 调度内核（dispatch/）

- 24 小时 × 96 个 15 分钟时段的混合整数线性规划，Google OR-Tools CBC 求解
- 决策变量：购电量、新能源消纳量、储能充放电功率、燃气轮机出力、可延迟算力负荷的时段分配
- 约束：功率平衡、SOC 动态、充放电互斥（96 个 0-1 变量）、爬坡率、并网容量、调度块内电量守恒、日末 SOC 目标
- 规模：约 770 个变量、290 条约束；单站 38–60 ms 求得最优解
- 目标函数：购电成本 + 碳排放成本 + 燃气燃料成本 + 储能循环损耗 + 最大需量电费（1.2 元/kW）

可复现的遥测模拟器按日周期、周周期、气象驱动制冷负荷与分时电价建模，随机项由「数据中心编码 + 日期 + 时段」的哈希确定性生成，不依赖调用顺序。

## 实测

调度结果（2026-10-23，四站实测，输入为模拟数据）：

| 数据中心 | 购电成本（元） | 降幅 | 购电峰值（kW） | 碳排变化 |
| --- | --- | --- | --- | --- |
| 北区 A | 9 109.81 → 7 973.61 | 12.47% | 764.17 → 679.56 | −1.2% |
| 南区 B | 7 682.07 → 6 756.64 | 12.05% | 611.78 → 555.49 | −1.7% |
| 东区 C | 11 472.39 → 10 080.74 | 12.13% | 962.71 → 866.80 | −1.3% |
| 西区 D | 4 245.53 → 3 047.03 | 28.23% | 470.98 → 258.45 | −25.84% |

三条策略在同一站点同一天的取舍（北区 A，2026-11-10，基线成本 8 899 元）：

| 策略 | 侧重点 | 结果 |
| --- | --- | --- |
| 成本优先 | 全成本最优 | 7 595 元（−14.7%） |
| 削峰优先 | 需量电费权重 ×3 | 峰值 522 kW（−23%），成本 +574 元 |
| 少买电 | 购电与碳排权重上调 | 购电 7 054 kWh（−32%），碳排 −6%，成本 +530 元 |

智能体侧：9 个工具（5 只读、4 写入需确认）、19 个单元测试；多轮上下文保存上一轮结构化意图与最近 6 句原话，30 分钟过期。

## 如何运行

本仓库是片段，**不能独立编译**：`ruoyi-agent` 依赖同工程的 `ruoyi-system` 与若依基础模块。放出来是为了让代码可读、可评审。

若要本地运行，需要完整工程（Spring Boot 3 + MyBatis + MySQL + Redis + Vue 2）：

```bash
mvn -DskipTests package -pl ruoyi-admin -am
java --enable-native-access=ALL-UNNAMED -jar ruoyi-admin/target/ruoyi-admin.jar
```

大模型接入是可选的：不配 Key 时自动走规则解析，配了就用模型解析，失败自动回落。Key 只从环境变量读取，仓库里永远是空串。

```bash
export DEEPSEEK_API_KEY=sk-xxxx
```

单独跑智能体模块的测试：

```bash
mvn -o test -pl ruoyi-agent -am \
  -Dtest=RuleIntentParserTest,AgentOrchestratorTest,FactGuardTest \
  -Dsurefire.failIfNoSpecifiedTests=false
```
