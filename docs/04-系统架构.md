# 四、系统架构

## 4.1 总体结构

前后端分离的 B/S 架构，单体后端 + 独立前端，共五层：

```
┌─────────────────────────────────────────────────────┐
│ 表现层   Vue 2 + Element UI + ECharts                │
│          运行看板 / 调度计划 / 预测 / 模型 / 设备     │
│          调度助手（对话式入口）                       │
├─────────────────────────────────────────────────────┤
│ 接口层   Spring MVC RESTful                          │
│          DashboardController / DispatchPlanController │
│          PredictController / ModelController          │
│          PotentialAnalysisController / HistoryController │
│          AgentController（/agent/chat…）              │
├─────────────────────────────────────────────────────┤
│ 智能体层 ruoyi-agent（可整体复制到其他项目）          │
│          AgentOrchestrator    状态机 + 三道闸         │
│          ToolRegistry         9 个白名单工具          │
│          CompositeIntentParser 大模型 + 规则兜底      │
│          LlmReplyComposer     正文改写                │
│          FactGuard            数字守门                │
├─────────────────────────────────────────────────────┤
│ 业务层   调度域（com.ruoyi.system.dispatch）          │
│          DispatchOptimizer    MILP 求解              │
│          ForecastService      预测评估               │
│          ForecastModels       四个模型               │
│          TelemetrySimulator   数据生成               │
│          PotentialAnalysisEngine 潜力回填            │
│          HistoryImportService 真实数据接入           │
│          DataPreProcessor     预处理算子             │
├─────────────────────────────────────────────────────┤
│ 持久层   MyBatis（框架与管理类）+ JdbcTemplate（分析类）│
├─────────────────────────────────────────────────────┤
│ 数据层   MySQL 8（业务数据） + Redis（缓存与会话）    │
└─────────────────────────────────────────────────────┘
```

## 4.2 模块职责

### 调度域（ruoyi-system）

| 类 | 职责 | 依赖 |
| --- | --- | --- |
| `DispatchModels` | 领域模型，全部为不可变 record | 无 |
| `DispatchDao` | 数据访问，参数化 SQL，批量写入 | JdbcTemplate |
| `TelemetrySimulator` | 构造可复现的负荷、光伏、电价序列 | DispatchDao |
| `ForecastModels` | 四个预测模型的实现 | 无 |
| `ForecastService` | 留出法评估、任务编排、模型训练 | DispatchDao、TelemetrySimulator |
| `DispatchOptimizer` | MILP 建模与求解、基线计算 | OR-Tools |
| `DispatchPlanService` | 计划生成、看板聚合 | 上述四者 |
| `PotentialAnalysisEngine` | 从计划差值回填四类潜力指标 | DispatchDao、IPotentialAnalysisService |
| `HistoryImportService` | CSV 导入与数据概览 | DispatchDao |
| `DataPreProcessor` | 预处理算子（纯函数） | 无 |

### 接口层（ruoyi-admin）

| 控制器 | 前缀 | 职责 |
| --- | --- | --- |
| `DashboardController` | `/dashboard` | 看板聚合、初始化、模型对比 |
| `DispatchPlanController` | `/system/plan` | 计划求解、列表、明细、对比、删除 |
| `PredictController` | `/data/predict` | 预测任务、结果、模型对比 |
| `ModelController` | `/data/model` | 模型台账、训练 |
| `DataImportController` | `/data/import` | 文件上传、预处理、导出 |
| `HistoryController` | `/data/history` | 历史数据概览与导入 |
| `PotentialAnalysisController` | `/system/analysis` | 潜力分析 CRUD 与回填 |

### 智能体层（ruoyi-agent）

单独一个 Maven 模块，只依赖 `ruoyi-system` 与 `ruoyi-common`，不依赖前端与框架服务，
整体复制到别的项目时只需替换工具实现。

| 类 | 职责 |
| --- | --- |
| `AgentOrchestrator` | 状态机 PARSE → GUARD → CONFIRM → EXECUTE → COMPOSE，三道闸与确认令牌 |
| `ToolRegistry` / `AgentTool` | 工具白名单；每个工具声明只读/写库与是否需要确认 |
| `CompositeIntentParser` | 大模型解析优先，失败或不可用时落规则解析 |
| `SlotNormalizer` | 站点、日期用原文覆盖模型猜测 |
| `LlmReplyComposer` / `FactGuard` | 正文改写与数字核对 |
| `dispatch/*Tool` | 9 个调度域工具：状态、计划、复盘、策略、重跑、撤销 |

模型调用走 `DeepSeekClient`（JDK HttpClient，约 100 行），不引入 LangChain4j 等重型依赖：
换厂商只改一个类，未配置 Key 时自动退化为纯规则模式。

## 4.3 技术选型与理由

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 应用框架 | Spring Boot 4.0.3 / JDK 17 | 生态成熟，与基座一致 |
| 权限 | Spring Security + JWT | 无状态，适配前后端分离 |
| ORM | MyBatis（管理类）+ JdbcTemplate（分析类） | 管理类字段多、复用代码生成器；分析类以批量时序读写为主，直接 JDBC 更简洁 |
| 求解器 | Google OR-Tools 9.11（CBC） | Apache 2.0，Java 原生绑定，无商业授权风险 |
| 数据库 | MySQL 8 | 通用、易部署 |
| 缓存 | Redis | 会话与字典缓存，框架既有能力 |
| 前端 | Vue 2 + Element UI + ECharts 5 | 与基座一致，图表能力足够 |
| 测试 | JUnit 5 + Surefire | 标准组合 |

## 4.4 关键设计决策

**决策一：为什么用 MILP 而不是启发式。**

储能的充放电互斥、燃机爬坡、可延迟负荷的块内守恒，都是线性约束；只有"充电或放电"是逻辑约束，
需要 0-1 变量。这恰好是 MILP 的典型形态。启发式能做，但无法保证最优性，也无法给出与基线的
可核对差值。MILP 单次求解 38–60 ms，成本可接受。

**决策二：为什么基线要单独算，而不是对比"上一版计划"。**

对比上一版计划只能说明"改进了"，无法说明"本来能省多少"。基线定义为"储能闲置、新能源优先、
电网兜底"的无调度运行方式，是一个客观参照物，任何人都能手工复算。

**决策三：为什么分析类模块用 JdbcTemplate。**

调度明细表单个计划 96 行、批量写入、按计划读取，没有复杂动态查询；用 MyBatis 需要为每张表
维护 resultMap 与 XML，收益低。管理类模块（策略、任务、设备）保留 MyBatis，与基座一致。

**决策四：为什么数据模拟器要可复现。**

算法效果必须能在别人机器上复现，否则实验结论不可验证。模拟器的随机项由
`(数据中心, 日期, 时段)` 的哈希确定性生成，同参数下结果逐字节一致。

## 4.5 部署拓扑

```
        ┌──────────┐
浏览器 ─┤  Nginx   ├─ 静态资源（ruoyi-ui/dist）
        └────┬─────┘
             │ /prod-api 反向代理
        ┌────▼─────────────┐
        │ ruoyi-admin.jar  │  8080
        │  Spring Boot     │
        └──┬───────────┬───┘
           │           │
      ┌────▼───┐  ┌────▼────┐
      │ MySQL  │  │  Redis  │
      └────────┘  └─────────┘
```

单机部署时前端可由 Spring Boot 直接托管静态资源（将 `dist` 放入 `resources/static`）。

## 4.6 非功能特性

| 项 | 现状 |
| --- | --- |
| 启动时间 | 冷启动约 8 秒 |
| 求解性能 | 96 时段 MILP 单站 38–60 ms |
| 导入性能 | 15 700 条历史数据约 40 秒（首次全量生成） |
| 并发 | 未做压测；求解为 CPU 密集，建议串行触发 |
| 可靠性 | 求解与回填带事务；预测与计划均落库，重启不丢 |
| 安全 | 全接口权限校验；口令支持环境变量注入；Druid 控制台限本机 |

## 4.7 设计系统

界面采用三层样式结构，避免颜色与尺寸散落在组件里。

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 设计令牌 | `src/assets/styles/design-tokens.scss` | 色阶、语义色、圆角、阴影、间距、动效曲线，以 CSS 变量暴露 |
| 主题覆盖 | `src/assets/styles/theme.scss` | 消费语义令牌，统一定义 Element UI 的圆角、阴影、聚焦环与过渡 |
| 图表主题 | `src/utils/chart-theme.js` | 图表配色、坐标轴与图例样式，三个图表页面共用 |

**颜色。** 主色为电力蓝 `#2a5fa6`，中性色为冷灰阶，状态色取绿 / 琥珀 / 红三档。
所有对外文本的对比度均实测：正文 10.31:1、次要文本 7.02:1、三级文本 5.43:1、
主色上的白字 6.39:1、输入框边框 3.51:1，均满足 WCAG 2.2 对正文 4.5:1 与非文本元素 3:1 的要求。

**形状与层级。** 圆角取 4 / 6 / 8 / 12 四档，嵌套表面遵循“外圆角 = 内圆角 + 内边距”。
结构性分隔（表格线、输入框边框）保留边框，纯层级关系（卡片、浮层）改用分层阴影，
以便在强制高对比模式下仍能通过透明边框绘制边界。

**动效。** 交互态使用 transition 而非 keyframes，并显式列出变化属性，从不使用 `all`。
按压反馈为 0.96 缩放、150 ms `cubic-bezier(0.2, 0, 0, 1)`，禁用态不缩放；
全部位移与缩放均置于 `prefers-reduced-motion: no-preference` 之下，
减少动效时退化为透明度变化。表格行悬停、页签切换等高频交互只做 150 ms 以内的背景过渡。

**可访问性。** 键盘焦点使用 `:focus-visible` 显示 2px 主色轮廓；侧边栏选中项同时用
底色、左侧色条与字重三重线索表达，不依赖单一颜色；浮层统一 `overscroll-behavior: contain`。
