# 十一、智能体演进路线（大脑优先版）

> 目标：先做出一个"大脑"——能对话、能自主跑、异常才找人。
> 基准排期 16 周，前 8 周交付可用大脑，后 6 周接设备。
> 版本 v0.4（2026-11-12），替代 v0.1 的"先铺轨道后装大脑"顺序；本周进展见 §0.1。
>
> **对外口径以 `doc/智能体调度方案_v0.2.docx` 为准。** 那份文档把六项能力按调度时序重命名，
> 并补了语音输入、L0–L4 监测分层、五类记忆与三处存储——本文的 W1–W6 排期与它一致，
> 但能力名称以那份为准。

## 0. 结论

1. **大脑优先，但"大脑"必须是"会调用工具的执行体"，不是聊天窗口。**
   判断标准只有一条：它能不能在你不在场的时候，把明天的计划解出来、校验过、发布掉。
2. **人机交互的真实形态是"卡片"，不是"聊天"。**
   日常 95% 零交互，4% 审批，1% 对话。所以把力气花在审批卡片和异常推送上，
   聊天框只是兜底入口。做一个漂亮的对话框、但没人用，是最常见的失败方式。
3. **目标不是"零人参与"，是"把人从操作移到监督"。**
   电力系统现阶段不可能全自动。可验收的目标是：日均人工干预从现在的十几次点击降到 **≤0.5 次**，
   且每次干预都是一次"决策"，不是一次"操作"。
4. **"手"要和"脑"同时长出来。**
   第 1 周只有 4 个只读工具（能查能答），第 2 周就有写工具（能改能做）。
   没有手的脑，第二周就会退化成问答机器人。

## 1. "大脑"到底包含什么

五件事，缺一件就不算完成：

| 能力 | 具体表现 | 反例（做了也不算） |
| --- | --- | --- |
| 理解 | 一句话 → 结构化意图 + 槽位（站点、日期、指标、约束） | 只做关键词匹配 |
| 规划 | 多步任务拆解与顺序执行（"重跑并和上周对比" = 3 步） | 一次只能执行一个固定动作 |
| 执行 | 调工具：权限、幂等、超时、重试、回滚 | 直接拼 SQL 或直接调 service |
| 表达 | 结论先行 + 证据链 + 可点的下一步 | 输出一大段散文 |
| 记忆 | 记住这次对话、这个站的脾气、上次为什么失败 | 每轮都从零开始 |

三条边界（决定它能不能上生产）：

- **不产数字。** 所有数值必须来自工具返回，带 `tool_call_id`。校验不到就重答或降级。
- **不做约束判断。** "SOC 够不够""需量会不会超"由 `plan.validate` 判定，不由模型判断。
- **不直连数据库、不直连设备。** 只通过 Tool 接口。这一条同时保证了可审计和可移植。

## 2. 人机交互怎么设计

### 2.1 三种模态，优先级从高到低

| 模态 | 占比 | 形态 | 建设优先级 |
| --- | --- | --- | --- |
| 静默自治 | ~95% | 无界面，只在日志与看板留痕 | 最高（W3） |
| 审批卡片 | ~4% | 主动推送到待办，一屏给结论 + 依据 + 三个动作 | 最高（W4） |
| 对话 | ~1% | 右下角抽屉，自然语言查询/指挥/追问 | 中（W1 起，W5 完善） |

### 2.2 对话里能做什么（动作白名单）

| 用户说 | 意图 | 调用 | 要确认吗 |
| --- | --- | --- | --- |
| 北区 A 昨天省了多少钱 | query | `report.summary` | 否 |
| 重跑明天北区 A 的计划 | command | `plan.solve` + `plan.persist` | 否，给撤销 |
| 把储能余量改到 20% | config | `strategy.update` | 是 |
| 批准 | approve | `approval.resolve` | 否 |
| 为什么建议少充 | explain | `plan.diagnose` | 否 |
| 停掉所有下发 | control | `plan.freeze` | 是，且双人 |

### 2.3 三条交互原则

1. **默认值优先于追问。** 缺参数就用默认值，把假设显式打在卡片上（"按 北区A / 明天 / 策略2 执行"），
   人点一下就能改。只在"动作不可逆"或"歧义会导致不同站不同结果"时才追问。
2. **一切可撤销。** 对话式操作误触率高，5 分钟内可 `undo`。可撤销是人敢放手的前提。
3. **单一写入口。** 前端按钮、对话指令、定时任务，三条路必须走同一套 Tool + 同一份审计。
   现在"生成计划"按钮直连 service，如果不改，agent 写的和界面写的必然打架，回放也不可能。

### 2.4 主动消息长什么样（W4 的验收物）

```
┌──────────────────────────────────────────────┐
│ 06:40  四站计划已生成                          │
│ 预计购电成本 4.82 万，较基线降 12.4%           │
│                                              │
│ ⚠ 西区 C 需确认：储能日末余量 12%，低于阈值 15% │
│   原因：光伏午后骤降 38%，为保消纳率优先充电    │
│                                              │
│ [ 接受计划 ]  [ 改为 20% 重解 ]  [ 查看曲线 ]  │
└──────────────────────────────────────────────┘
```

一屏给全：结论、数字、风险、原因、三个动作。**人只需要点一次。**

```
                    ┌──────────────┐
   对话 / 审批卡片 ──┤  会话层       │  SSE 流式、会话持久化
                    └──────┬───────┘
                           │ Intent（结构化）
                    ┌──────▼───────┐
                    │  决策层       │  规则策略 / LLM 策略 / 混合
                    │  + 记忆       │  情景记忆、站点画像、偏好
                    └──────┬───────┘
                           │ Action（枚举）
                    ┌──────▼───────┐
                    │  治理层       │  权限、幂等、二次确认、审计
                    └──────┬───────┘
                           │ ToolCall
                    ┌──────▼───────┐
                    │  工具层       │  求解/预测/校验/发布/复盘
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
        现有调度域（MILP/预测）     设备网关（W11+）
```

模块（可复制性的载体，第 1 周就按这个建目录）：

```
agent/
├── agent-core/            零业务、零 Spring：Intent/Action/Tool 契约、状态机、记忆抽象
├── agent-runtime-spring/  会话、SSE、调度、落库、审批
├── agent-host-ruoyi/      若依适配：权限、菜单、审计
├── agent-device/          设备网关（W11 起）
└── packs/dispatch-pack/   本项目领域包：工具实现、策略、评测集
```

铁律：`agent-core` 里不出现"数据中心""调度"字样，也不依赖 `com.ruoyi`。
验收方式是 `mvn dependency:tree`，不是自我感觉。

## 5. 前 6 周要做什么（详细）

### W1 脑骨架：能听、能看

- `agent-core`：`Intent`、`Action`、`ToolCall`、`Observation` 四个 record；`Tool` 接口（含 `sideEffect`、`idempotencyKey`、`timeout`）；`LlmClient` 接口。
- **不要引入 Spring AI 之类的重框架。** 一个 HTTP + JSON 的薄客户端就够，三十行。
  理由：要自己控结构化输出、重试、降级；重框架会把版本和厂商绑进去，也和"core 零依赖"冲突。
- 只读工具 4 个：`state.snapshot(dc)`、`plan.list(dc, days)`、`plan.detail(planId)`、`report.summary(dc, date)`。
- 会话表：`agent_chat`、`agent_message`；SSE 流式返回。
- 前端：右下角抽屉，回答里数字带脚注（工具名 + 数据时间）。
- 意图识别先做**有限枚举**（query / explain / command / approve / config），不做开放式。
- 验收：10 个真实业务问题答对 9 个；第 10 个允许答"我查不到"，但不许编。

### W2 长出手：能改、能撤

先拆现在的耦合——`DispatchPlanService.generate()` 把求解和落库放在同一个事务里，
工具重试就会重复插计划：

| 现在 | 拆成 |
| --- | --- |
| `generate(dc, strategy, date)` | `solve(...)` 纯计算 → `persist(outcome, idemKey)` 落库 |
| 失败抛 `IllegalStateException` | 返回 `SolveFailure(reason, bindingConstraints)` 供诊断 |

新增两个东西：

- **`plan.validate(planId)` 校验器**：功率平衡、SOC 余量、需量、并网容量、消纳率下限。
  这些现在隐含在求解器里，一旦人工改计划、回滚、换真实数据就没人复核了。校验器是 agent 敢自动跑的前提。
- **撤销**：每个写动作登记 `undo` 句柄，5 分钟内可回退。

- 单一写入口：把前端"生成计划"按钮改成调同一工具，删掉旧路径。
- 验收：说"重跑北区 A 明天计划"能完成；重复说两遍只有一份；点撤销能回退。

### W3 自主运行：少人的第一步

- Quartz 时序：06:00 预测 → 06:15 求解 → 06:25 校验 → 06:30 发布 → 每 15 min 滚动 → 23:00 复盘。
- 状态机持久化，重启可续跑；单站串行锁（顺手解决遗留 L5 的并发求解）。
- 降级表：

| 故障 | 降级 |
| --- | --- |
| 数据不完整 | 跳过该站，沿用昨日计划并标注 |
| 求解不可行 | 放松顺序：消纳率下限 → 日末 SOC → 需量上限，最多 2 次 |
| 求解超时 | 放宽 gap 重解一次，仍超时用基线 |
| LLM 不可用 | 切规则策略，功能不中断 |
| 下发失败 | 单条重试 3 次，失败冻结并告警 |

- 验收：模拟时钟跑 7 天，人为注入 5 类故障，不崩、不重复、可追溯。

### W4 审批：交互的真正形态

- 阈值表：节省率 <3%、SOC 余量 <15%、需量 ≥95%、连续 2 次不可行、单动作影响 >5% 负荷。
- 卡片模板：结论 / 数字 / 风险 / 原因 / 三个动作（第二个是"调参重解"）。
- 待办列表 + 站内信 + 邮件；一屏决策，不需要再点进另一个页面看曲线。
- 验收：5 个异常场景，每个只需 1 次点击。

### W5 解释：从"能跑"到"可信"

- 不可行诊断：读求解器 `message` 与绑定约束 → 人话 + 建议动作（放松哪个、放多少）。
- 复盘周报：四项指标、两次关键决策、一条改进建议。
- 评测集 25 例：电价尖峰、光伏骤降、SOC 偏低、预测漂移、设备离线、需量逼近上限、
  数据缺口、连续不可行……断言三件事：该调哪个工具、该不该挂起、该不该找人。
- 数字溯源：回复里每个数值必须带 `source_tool_call_id`，校验不到整段拒绝。
- 验收：通过率 ≥85%，0 幻觉数字进计划，p95 决策 <8s。

### W6 记忆：让它越跑越准

- 三层：工作记忆（本次会话）、情景记忆（决策 + 结果，可检索）、站点画像（PV 波动、储能效率、常触发约束）。
- 偏好："以后储能余量按 20% 留" → 写入策略偏好，版本化、可撤销、下次生效。
- 验收：能回答"上周三为什么少充 200 kWh"，并给出计划/实际/偏差三段证据。

## 6. 大脑的工程约束

| 项 | 做法 | 为什么 |
| --- | --- | --- |
| 结构化输出 | JSON Schema 校验，失败重试 1 次后降级 | 模型输出不可靠，必须兜底 |
| 数字溯源 | 每个数值带 `tool_call_id` | 防幻觉进计划 |
| 动作枚举 | 只允许白名单动作，禁止自由生成 | 缩小爆炸半径 |
| 幂等 | `idemKey = hash(站, 日期, 策略, 参数)` | 对话易重复触发 |
| 确认分级 | 只读 / 可逆写 / 不可逆写（后者二次确认 + 双人） | 平衡效率与风险 |
| 权限 | agent 服务身份 + 发起人上下文，取两者权限交集 | 防越权 |
| 超时与预算 | 单次决策 ≤20s、工具调用 ≤4 轮、token 上限 | 防卡死与成本失控 |
| 降级开关 | `agent.policy=rules\|llm\|hybrid`，默认 hybrid | 出事一行配置切回规则 |
| 审计 | 每步落 `agent_step`，人改与机改同一张表 | 可回放、可追责 |

## 7. "减少人参与"的三个杠杆

| 杠杆 | 做法 | 效果 |
| --- | --- | --- |
| 覆盖 | 把"人要不要做"变成阈值表里的规则 | 把 90% 的日常动作变成无人值守 |
| 可逆 | 每个动作有回滚点，5 分钟撤销 | 人才敢不盯着 |
| 置信度 | agent 给置信度，低于阈值才找人 | 从"全问"变成"只问该问的" |

度量（这几项每周记录，W9–W10 的观察期就是看它们的曲线）：

- 日均人工干预次数（目标 ≤0.5）
- 无人值守完成的日计划占比（≥95%）
- 审批卡片平均决策时长（目标 <30s）
- 建议采纳率（≥80%）
- 撤销率（>5% 说明阈值设错了）

## 8. 硬件（W11 起，原则不变）

- 协议顺序：Modbus TCP → MQTT → OPC UA → IEC 104/61850。
- 网关独立进程，不塞进单体：故障隔离、可现场调试。
- **影子两周**：只记录不执行，采纳率 ≥80% 才进实控。
- 联锁写在网关侧硬编码，不依赖 agent、不依赖网络。
- 实控只碰非关键负荷（可延迟算力、制冷设定点），不碰并网断路器。
- 硬件采购与协议文档必须在 **W9 前**启动，否则 W11 空转。

## 9. 风险

| 编号 | 风险 | 应对 |
| --- | --- | --- |
| R1 | 做成聊天机器人，不能干活 | W2 必须交出写工具，否则视为失败 |
| R2 | 对话误操作 | 撤销 + 二次确认 + 动作白名单 |
| R3 | 双轨写入（界面一套、agent 一套） | 单一写入口，W2 就改，不留到后面 |
| R4 | 幻觉数字进计划 | 溯源校验 + 不产数 + 校验器兜底 |
| R5 | 模型不可用/涨价 | 薄客户端可换厂商 + 规则策略降级 |
| R6 | 审批疲劳（推太多，人不看） | 阈值从宽到严，先只推 3 类；统计采纳率反向调 |
| R7 | 范围膨胀 | M1–M5 里程碑，每级可独立交付 |

## 10. 模型选型（已定）

**外接 DeepSeek API。** 分工如下，理由见 `doc/智能体能力方案_讨论稿.docx` 第 6.4 节：

| 模型 | 用在哪 | 为什么 |
| --- | --- | --- |
| `deepseek-chat` | 主控：意图识别、选工具、写解释 | 支持函数调用、响应快、便宜 |
| `deepseek-reasoner` | 离线：不可行归因、周报生成 | 推理更强，但不支持工具调用、慢 |

仍然保留的两条退路：`agent.policy=rules` 一行配置切回纯规则；`LlmClient` 是薄接口，换厂商只改一个类。
